## Orchestrator completion standards

All three phases consider simplicity, sound design, readability, performance, scalability, and backend durability alongside correctness. Apply these to the requested behavior with evidence rather than generic checklists or speculative infrastructure. Planning specifies what survives failure and how recovery completes; development implements those invariants; review verifies them across the backend, not only the LLM path.

- **Planning:** Every phase has an intended outcome, prerequisites, ordered steps, and an exit criterion. Every step states the concrete change, affected modules/contracts, dependencies, implementation approach sufficient to finish it, expected success/failure behavior, and how to verify completion. Name exact commands where they exist; otherwise specify the check to implement rather than inventing runnable commands. Resolve correctness-critical decisions during planning through repository inspection, available tools, focused experiments, and established project choices. Do not leave agent-resolvable decisions as future blockers; record a concrete resolution or the specific external input still required. Avoid vague steps such as "implement persistence" or "add tests." Include relevant async boundaries, query shape, resource limits, durability semantics, and capacity assumptions. Keep details proportional to the work; do not prescribe every line of code or add artificial phases to a small fix.
- **Development:** Follow the step's completion criteria and update the plan when implementation evidence changes them. Inspect every new blocking I/O or substantial CPU operation reachable from async code, choose a safe execution boundary, and verify it. Preserve readable dependency boundaries and efficient data access; avoid N+1 queries, unbounded task creation, and unbounded result/history loading. Complete focused behavioral checks and diff review before reporting a step finished; distinguish implemented, verified, and still-pending work.
- **Review:** Assess whether the requested behavior is correct, simple, well designed, readable, performant, and scalable within stated capacity limits. Trace relevant calls across HTTP, services, persistence, and integrations; check blocking operations, query growth, resource ownership, failure recovery, and test evidence. Report concrete defects with file/line, trigger, consequence, and a proportionate fix. Separate optional suggestions from actionable findings; do not turn stylistic preferences into defects, request speculative abstractions, or apply unsolicited fixes. State verification gaps and do not claim scalability from lint/type checks alone.

Example planning step: "Implement request admission in the conversation application service and persistence layer using the accepted unique request key and one-active-request constraint. Commit the request/user message before external calls, map duplicate/busy cases according to the lifecycle table, and return materialized records from the worker-thread unit. Done when deterministic races with same and different IDs against a temporary SQLite file produce the specified status, message count, and provider-call count." The enclosing phase completes only when its API, persistence, failure, and restart criteria pass.

## Python/FastAPI performance and scalability

Backend-architecture and backend own execution/resource boundaries; persistence owns query efficiency; verification owns evidence. Apply the existing session rules without converting trivial pure synchronous helpers into async functions or offloading them unnecessarily.

- Use awaited async clients for network I/O; construct and close reusable HTTPX clients in application lifespan and inject them so connections are pooled. Do not create clients in hot loops. Apply explicit timeouts and bounded connection/concurrency limits.
- Offload blocking I/O as complete units. Threads protect event-loop responsiveness but are not a general CPU-parallelism strategy; keep substantial CPU work off the request event loop and choose further execution machinery only for demonstrated workload needs. Account for worker saturation and cancellation; thread work may outlive cancellation.
- Filter, order, and limit inventory/history in SQL. Select only needed data and use explicit joins or eager/batched loading when relationships are needed. Never fetch each related record in a per-row loop or allow response serialization to trigger lazy SQL. Add indexes for actual filter/order/uniqueness access paths; inspect query plans where a hot query warrants it rather than indexing every field.
- Test N+1 risk with multiple parent/related records and SQL query counts as result size increases: require a bounded/batched query shape, not one extra query per row. Include serialization in the measured path. Use representative larger, clearly labeled synthetic test fixtures; these do not replace validation against `docs/context/inventory/data.csv`.
- Bound page sizes, request sizes, model context, tool results, simultaneous external calls, and total run duration. Define overload behavior instead of an unbounded queue. Retain full persisted history while selecting bounded complete turns for model context without splitting tool-call/result pairs; preserve authoritative selected-vehicle context separately.
- Planning specifies realistic workload assumptions and measurable acceptance budgets for affected hot paths. Development records query counts and targeted measurements; review checks evidence. Prefer deterministic query/resource assertions in CI and separate measured latency/load checks from brittle timing tests. Profile before adding caches or micro-optimizations; any cache needs a freshness/ownership decision, especially for safety data.
- Scalability initially means bounded work and memory, efficient queries, concurrency across conversations, and documented capacity limits. The accepted single-worker SQLite volume is not horizontally scalable. Record the measured trigger and necessary coordination/storage changes for outgrowing it; do not add multiple workers, PostgreSQL, queues, or distributed locks within this prototype by default.

## Backend durability and recovery

Backend-architecture owns failure and recovery boundaries; backend owns request/lifespan behavior; persistence owns atomic writes and integrity constraints; Docker owns persistent storage and shutdown configuration; backend-verification owns failure-injection and restart evidence. Apply this guidance to every affected backend state-changing path, including the pending import of `docs/context/inventory/data.csv`. Reuse the accepted chat lifecycle rather than creating competing retry/recovery semantics.

- Define the durable state, atomic unit, commit point, and outcome of failure for each write path. Enforce relational invariants with database constraints. Roll back failed units; never acknowledge a successful write before commit or silently replace unavailable persistent storage with temporary/in-memory state. Preserve previously committed data on subsequent failures.
- Handle database contention, failed writes, external-service outages, and cancellation explicitly. Bound waits and retry only understood transient, safe operations; never blindly replay a write whose commit outcome is uncertain. Resolve ambiguous outcomes from durable identifiers/state where supported, otherwise return a clear error requiring reconciliation. Keep error responses sanitized and diagnostic logs correlated to the request.
- Give sessions, clients, tasks, and other resources explicit lifecycle ownership and cleanup on success, failure, and cancellation. Keep required persistence out of untracked fire-and-forget work. On shutdown, stop admitting new work and allow a bounded drain before interruption; abrupt termination must still be recoverable through the accepted startup rules. Graceful cleanup is not the sole durability mechanism.
- Validate essential configuration and persistent storage access before serving writes. Startup recovery must be safe to repeat after another interruption and must not reset existing data. If storage cannot be opened or recovery cannot complete, fail startup clearly rather than serving with lost state. Health reporting should describe local service/storage readiness without depending on live LLM/NHTSA calls.
- Test rollback after a mid-unit failure, constraint violations, bounded lock contention, storage write failures without false success, cleanup after exceptions/cancellation, and preservation of committed state across process restart/container recreation. Use real temporary SQLite for transactional/restart assertions and injected faults for otherwise impractical failures. Include an abrupt-stop integration check when the backend is scaffolded; application-object recreation alone does not prove crash recovery.
- Document the guarantee boundary: process/container restart preservation assumes the persistent volume remains intact. Volume deletion, disk loss, backup/restore, high availability, and automatic interrupted-run resumption are outside the current prototype guarantee. Do not weaken storage durability settings for speed without an explicit, documented decision; do not introduce disaster-recovery infrastructure by default.

For each affected planning step, name the relevant failure scenario, expected persisted state/API outcome, recovery action, and verification. Development completes those checks; review looks for partial writes, false success, leaked resources, unsafe retries, destructive startup behavior, and recovery dependent only on in-memory state. A narrow read-only change need not exercise the entire durability suite.

## Reliable LLM behavior

Chat-agent owns these rules with persistence, NHTSA, and backend-verification. Reliability is observable behavior under failure, not a promise that the provider always succeeds.

- Follow the accepted admission, persisted outcome replay, complete-turn history, and interruption lifecycle. Test failures before and after durable writes and ensure retries do not duplicate messages. Automatic interrupted-run resumption, exactly-once provider execution, and durable workflow engines remain deferred.
- Set an overall run deadline and bounded provider/tool/validation attempts, tool-call count, context size, and output size. Coordinate SDK and application retry budgets to prevent multiplying retries. Retry only classified transient failures when the operation is safe, within the remaining deadline, with bounded backoff; respect provider retry guidance. Do not retry invalid configuration indefinitely or silently rerun terminal requests.
- Validate tool inputs and outputs, constrain inventory access to application-owned queries, and ground vehicle/safety claims in retrieved records. Treat user and retrieved content as data, not authority to change tool permissions. Preserve unavailable/partial safety data distinctions; resolve ambiguous vehicle references through clarification rather than guessing.
- Keep prompts and tool definitions in source control and identify provider/model configuration for reproducibility. Maintain deterministic fake-based tests for malformed outputs, exhausted budgets, transient/permanent failures, ambiguous follow-ups, unsupported claims, and interrupted history. Keep a small optional live evaluation set with expected factual/tool behavior separate from CI; avoid exact prose assertions.
- Include lightweight diagnostic evidence: request/conversation correlation IDs, operation duration, outcome/error category, and provider/tool attempt counts; token usage when available. Exclude secrets and raw conversation/tool payloads by default. Use this evidence to diagnose reliability, latency, and cost without adding a comprehensive observability platform.

## Architecture guidance and agent failure modes

Both architecture skills should give concrete decisions and evidence requirements, not a generic clean-code checklist. During implementation, maintain one short `docs/architecture.md` with backend, frontend, and shared API-boundary sections describing actual module responsibilities, dependency direction, state owners, and representative implementation paths. Create it with the first implemented slice and add frontend details when implemented. Each architecture skill maintains its side; both coordinate shared boundaries with api-contract. Link the relevant sections from each skill and keep significant tradeoffs in README and pending changes in plans. Do not duplicate the architecture map in every skill or invent a utility catalog before code exists.

| Failure mode to address | Guidance and observable outcome |
| --- | --- |
| Adding a second helper or service without inspecting existing code | Search implementations and callers first. Reuse an existing function when its meaning, validation, and failure behavior fit; otherwise explain the relevant difference. |
| Forcing unrelated behavior into one generic helper | Extract shared behavior when real callers share the same semantics and reason to change. Keep feature-specific helpers close to their feature; avoid a miscellaneous utils module or speculative base classes. |
| Putting database, model, or NHTSA behavior into routes | Keep routes responsible for HTTP validation/mapping and delegate use cases to application services. Keep inventory queries and safety behavior in ordinary services with thin tool wrappers. |
| Leaking library formats across boundaries | Keep ORM entities separate from public API schemas, Pydantic AI serialization at its integration boundary, and assistant-ui conversion in the frontend adapter. Prevent lower-level business behavior from depending on HTTP or UI concerns. |
| Creating conflicting sources of truth | SQLite owns persisted conversation/message history and selected-vehicle context. Browser state is a view of backend state; public API contracts drive generated frontend types. |
| Adding hidden global dependencies or import-time I/O | Construct dependencies explicitly at application setup; supply database and external clients to their consumers so meaningful tests can replace them. |
| Putting transport and chat orchestration into presentation components | Frontend architecture keeps API transport and assistant-ui conversion in their adapters; components and focused hooks own UI interactions and rendering. Reuse existing paths before introducing another layer. |
| Duplicating derived UI state or extracting overly broad hooks | Frontend architecture identifies the minimal state owner, derives values where possible, and extracts hooks only around cohesive behavior with matching lifecycle semantics. |
| Copying an obsolete pattern or creating a parallel replacement | Inspect the current representative path and affected callers. For an authorized replacement, update affected callers/tests/docs together and remove obsolete code within scope. Do not preserve legacy paths just to satisfy old tests. |
| Refactoring unrelated areas in pursuit of consistency | Keep structural work tied to the requested behavior. Record unrelated findings without expanding the change. |
| Writing tests that simply mirror the new implementation | Verification skills require behavioral assertions at the relevant boundary, including failure cases, using real temporary persistence where durability matters. |

Apply this authoring lens to every specialist: identify a concrete failure mode, give the decision rule that prevents it, and define the evidence that the work is correct. Add guidance for demonstrated project problems as they emerge; avoid accumulating hypothetical rules or generic language tutorials. Significant architecture decisions should briefly identify code placement, reused components, dependency/state implications, and the tests that validate the affected behavior.

Validate both architecture skills with existing reusable helpers and similar-looking helpers with different semantics. Backend scenarios cover business logic placed in a route, transaction ownership, and library serialization leaking into public schemas. Frontend scenarios cover duplicated hooks, redundant derived state, transport logic in components, and duplicate API types. Routing scenarios cover a frontend-only hook extraction, a backend-only repository change, a change to conversation ownership across the API boundary that needs both, and a small local fix that should not trigger broad refactoring.
