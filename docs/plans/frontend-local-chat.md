# Localhost chat frontend

Created: 2026-09-10 (America/Chicago).
Status: implemented; deterministic checks and browser restart acceptance passed. See [implementation evidence](frontend-implementation-evidence.md). Live configured-model smoke returned provider_error.

## Outcome and scope

Open `http://localhost:5173`, chat with AutoAssist about inventory and specific vehicles, ask recall/crash-rating follow-ups, and reload to continue the same backend conversation. Build one readable chat screen with a multiline composer, progress/error states, and a New chat action. This is a local browser interface, with no installable app or hosting requirement.

Use the accepted React, strict TypeScript, Vite, assistant-ui, native fetch, plain CSS, npm lockfile, and Docker Desktop stack. Keep authentication, conversation sidebar/search, model settings, vehicle cards, attachments, voice, streaming, edit/regenerate/cancel, and production deployment outside this slice. The frontend uses admission, request-status, and history endpoints backed by PostgreSQL.

Steps 1–2 provide the chat contract. [Step 3](step-3-nhtsa-safety.md) is currently being implemented and intends to keep that public contract unchanged: safety information arrives in assistant text. Frontend scaffolding and inventory-chat work can proceed against step two; integrated safety acceptance requires completed step three. Do not modify its in-progress backend files. Step four remains the API verification/handoff effort; reuse its verification entry point when available rather than creating competing automation.

| Operation | Current contract used by the UI |
| --- | --- |
| Discover dealership | `GET /dealerships`; resolve configured public slug `mia-motors` to its returned UUID/name. Missing slug or failed loading produces an actionable setup error, not a different dealership. |
| Create conversation | `POST /dealerships/{dealership_id}/conversations` with `{creation_id}`; 201 returns `id`. Retain the creation UUID for retries. Backend chooses its configured connection. |
| Send text | `POST /dealerships/{dealership_id}/conversations/{conversation_id}/messages` with `{request_id, text}`; 202 confirms admission; terminal replay returns the stored HTTP status/body. Text is nonblank, maximum 4,000 characters. |
| Read request status | `GET /dealerships/{dealership_id}/conversations/{conversation_id}/requests/{request_id}`; 200 contains active or terminal status. Terminal states include the stored reply or error in `outcome`. |
| Restore history | GET on the same messages path, `after_sequence=0&limit=100`; follow `next_after_sequence`. Items contain stable IDs, sequence, request ID/status, text, role, and error code. |
| Errors | Application errors use `{error:{code,message}}`; 422 uses FastAPI validation details. Interpret status and code, including individual 409 outcomes, rather than assuming every fetch resolution succeeded. |

The [shared request lifecycle](../stack-baseline.md#chat-request-lifecycle) remains authoritative. PostgreSQL owns messages, vehicle context, admission and terminal commits. Browser storage contains only a conversation pointer and a recoverable pending request; never upload browser history as model context. A reply is durable only after the server reports committed completion. A network failure leaves the outcome unknown.

Use one React-owned conversation controller with assistant-ui **ExternalStoreRuntime**. This is the baseline's permitted alternative to LocalRuntime: exact projection of admitted/failed/interrupted server messages and separate unaccepted drafts avoids reconciling a second optimistic runtime transcript. Keep that controller local to the chat root; no global store. Provide only supported runtime callbacks. Current official docs describe external messages, conversion, and capability-based callbacks; confirm compatibility against the pinned installed version during scaffolding. [ExternalStoreRuntime](https://www.assistant-ui.com/docs/runtimes/custom/external-store), [LocalRuntime](https://www.assistant-ui.com/docs/runtimes/custom/local-runtime).

## B. Complete send, restore, and recovery behavior

Prerequisite: A's typed fetch boundary and runnable shell.

1. Add `src/chat/useConversation.ts` as the sole owner of server-message projection, history loading, draft/pending identity, and submission state. `src/chat/runtime.tsx` converts that state to assistant-ui; `src/chat/ChatScreen.tsx` renders it. HTTP handling stays in the client. Trigger writes only from deliberate actions, never mount effects.
2. Resolve the dealership, restore a local-storage conversation pointer scoped to API origin/dealership, and load server history before enabling continuation. Read 100-message pages in ascending sequence, upsert by server ID (updating request_status/error_code on existing messages), and reject nonadvancing cursors. Terminal request states take precedence over in_progress, including when an older read finishes later; never downgrade an observed terminal state. Keep message order by sequence. Bound each restore action to ten pages; if more remain, offer Continue loading and keep sending disabled until restoration completes. This avoids silent truncation and unbounded startup requests. A failed page retains earlier data and supports retry. A validated API 404/not_found for the current conversation enters the missing-conversation recovery state in B.6; proxy HTML, malformed errors, and transport failures do not establish that the conversation is missing.
3. Create lazily on first Send, save the returned conversation ID, then allocate one UUID for that intentional text submission. Save its exact payload and conversation identity before posting. Prevent duplicate keyboard/click submission while pending. Render pending text separately until reconciled with admission; never fabricate an assistant message. If creation's response is lost, report that creation was unconfirmed and allow explicit creation retry; the browser retains its client-generated creation ID across retry and reload, and the server returns the same dealership-scoped conversation. The text is submitted only after creation is confirmed.
4. On 202, reconcile the committed user message and poll status at most 20 times with 0.5, 1, 2, 4, then 5-second capped delays. On completion, merge server messages by ID/sequence and clear pending recovery data. Terminal failure or interruption settles the request without fabricating a reply. Transport loss, malformed responses, or poll exhaustion retain the same ID/text and expose Check reply. This action uses GET for confirmed admission and same-ID POST for uncertain admission. Reload polls server-confirmed active history without POST. Reconcile from the unresolved user sequence minus one, or zero if unknown, with the ten-page-per-action history bound. Keep sending disabled while reconciliation or the request remains unresolved. Ignore responses from an inactive view generation.
5. Map `conversation_busy` to unaccepted submission with preserved text/ID; retry later using that identity. Treat `202` with `status: in_progress` as accepted work still running. Treat `request_id_conflict` as a reconciliation error, never silently mint a replacement ID. Persisted provider failure/timeout or interruption displays on the admitted user message; Try again is a deliberate new submission with a new ID. For 422 preserve editable draft; for `server_busy` preserve the unaccepted request. For other 503/500 outcomes reconcile history before claiming admission or failure. Backend-offline errors never create a fake reply.
6. Reload merges persisted history with the saved pending record by request ID. Completed/failed/interrupted server states supersede local hints. If an in-progress item has no local recovery record, its server request ID/text permits Check reply with the same payload. Storage failure is visible; in-memory chat can continue but must not promise reload recovery. Disable New chat while submitting/unresolved, except after a definitive missing-conversation result. In that state, show that the old conversation is unavailable and enable explicit New chat recovery even when a pending record exists. On that action, preserve the pending text as an editable draft, clear the obsolete local conversation pointer and pending request identity, invalidate outstanding operations for the old view, and return to lazy creation. Do not infer the old request outcome or automatically create a conversation/send the draft; only a later deliberate Send creates the new conversation and allocates a new request ID. If clearing browser storage fails, show the existing reload-recovery warning. Ordinary New chat resets only the active browser pointer and view, creates lazily, and never deletes backend history. This version restores the most recent chat only. Guard all history and submission responses by originating conversation/view generation so late results cannot replace a new view or restore its obsolete pending record.

Exit: deterministic browser tests capture actual outgoing IDs/text for send, double-submit, lost-response retry, busy versus in-progress, terminal failure/new attempt, reload, malformed responses, storage failure, and New chat. Visible transcript contains only admitted users and actual replies, in order without duplicates. Test multi-page restore, page failure/retry, and the loading bound. Start with a loaded in_progress user message and change it to failed or interrupted without adding a sequence: Check reply must update that same message and release the unresolved lock after reconciliation. Deliver a stale in_progress history response after a terminal result and verify the terminal status remains. With a saved pointer and pending payload, return a validated conversation 404: New chat must be enabled, clear the obsolete recovery identity, retain editable text, and make no creation/submission call until deliberate Send; that Send uses a new conversation/request ID. Verify transport errors and malformed/proxy 404s retain the unresolved lock, and late old-view responses cannot repopulate the recovered view. Use Playwright for these focused browser/adapter cases and the small smoke suite; no second component runner is needed initially.
